# 2026-10 리팩토링·개선 프로그램 실행 계획

관련 Issue: 우산 [#530](https://github.com/MyKnow/ssartnership/issues/530), 이 문서의 기록 단위 [#538](https://github.com/MyKnow/ssartnership/issues/538)(RF-01)

PVE 자체 호스팅 이전(Issue #523) 직후 진행한 3차 코드베이스 점검(구조, 성능·UX·운영, 보안·데이터·복원력)의 결과를 25개 작업 단위(RF-01~RF-25)로 나눠 반영한다. 이 문서는 단위들이 공통으로 따르는 **기본 결정**과 진행 규칙을 저장소 안에 고정한다. 단위별 범위·PR 분할·검증 결과는 각 단위 Issue와 PR이 정본이다. 점검 원본(후보 목록·수치)은 저장소에 커밋하지 않은 로컬 작업 자료이며, 이 문서는 그중 결정과 규칙만 옮긴다.

## 진행 규칙

- 모든 단위는 `origin/dev`에서 `<type>/<issue>-<slug>` 작업 브랜치를 만들고, 마지막에 통합 브랜치에서 병합 순서·충돌·전체 검증을 확인한 뒤 `dev`로 보낸다. `main` 승격은 통합 검증과 운영자 승인 뒤다.
- 단위는 자기 범위의 파일만 바꾼다. 다른 단위와 같은 파일을 건드리면 PR에 명시하고 통합 단계에서 조정한다.
- 각 단위는 완료 전에 `npx tsc --noEmit --pretty false`, 변경 파일 ESLint, `npm run test:node`를 통과하고, 문서·마이그레이션·의존성 변경 시 각각 `npm run check:docs`, `npm run validate:migrations`, `npm run check:lockfile`을 추가로 실행한다.
- 파일 이동·개명·문자열 변경은 `grep -rl "<경로|식별자|문자열>" tests`로 소스 텍스트 계약 테스트를 찾아 **같은 커밋**에서 갱신한다. 절차 세부는 [`ssartnership-patterns` 스킬](../../../.agents/skills/ssartnership-patterns/SKILL.md)의 리팩토링 절차를 따른다.
- 외부 시스템에 대한 비가역 조치(GitHub 시크릿 삭제, 클라우드 키 폐기, 라이브 DB DDL 적용, PVE 호스트·systemd 실적용, 브랜치 보호·라벨 변경, 외부 메시지 발송)는 단위가 실행하지 않는다. 코드·문서·스크립트로 가능한 데까지 준비하고 운영자 조치로 넘긴다.
- 저장소는 공개 저장소다. 시크릿 값, 보관 위치, 계정, 내부 주소, 취약점 세부는 커밋·Issue·PR에 쓰지 않는다. 운영자 조치의 보안 상세는 저장소 밖 로컬 운영자 문서에만 두고, 공개 기록에는 "운영자 조치 N건"처럼 일반화한다.

## 운영자 결정 대기

아래는 기본값으로 정하지 않은 항목이다. 결정 전까지 관련 단위는 문서·준비 작업까지만 한다.

- 백업 사본 보존 개수, 파기 뒤 백업에 남는 기간의 허용 창, 복구 키 오프라인 보관과 2차 수신자 여부
- 디스크 역할 표기의 정본(저장소 감시 설정과 운영 스킬 중 어느 쪽이 맞는지) 확인
- 클라우드 프로젝트·키 폐기와 GitHub 시크릿 삭제 승인
- 처리방침 v4 재동의 시점(행사·학기 일정 고려)
- `dev` 브랜치 force-push·삭제 차단, Public Readiness push 트리거 정리, Actions 실패 원장 물리 분할 시점
- 앱 VM의 로컬 감시 스택(Prometheus·Alertmanager·Grafana)을 공용 감시의 폴백으로 남길지, 아니면 공용 감시 하나로 정리할지
- 공개 저장소에 이미 기록된 인프라 정보(내부 주소·VM 배치·백업 경로)를 줄일지와 그 범위. 결정 전에도 위 진행 규칙에 따라 새로 쓰지 않는다.
