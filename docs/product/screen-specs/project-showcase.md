# 프로젝트 쇼케이스 이벤트 화면 계약

작성 기준일: 2026-09-26
범위: 「내 프로젝트를 소개합니다!」 출품·체험·발표 화면과 운영 화면. 운영 규칙은 [기능 명세](../../specs/project-showcase-event/spec.md)를 따른다.

## 공통 정책

- 모든 화면은 `/events/project-showcase/**`와 `/admin/events/project-showcase/**` 아래에 둔다.
- 단계(준비·중단·예정·모집·확인·체험·검증·발표·종료)는 운영자가 설정한 일정과 활성화 여부로만 계산한다.
- 프로젝트 내용은 체험 기간에만 공개한다. 학번·팀원 명단을 받지 않는다. 공개 당첨 명단에는 마스킹 이름만 표시한다.
- 출품·일정·검수 입력은 `src/lib/project-showcase/validation.ts`의 같은 함수를 FE와 BE에서 쓰고 첫 오류 필드에 focus한다.

## `/events/project-showcase` — 이벤트 허브

- 목표·위계: 히어로 → 진행 상태 카드(단계, 다음 일정, 주요 버튼) → 일정 3단계 → 단계별 본문(모집: 출품 가이드, 체험: 프로젝트 갤러리, 발표·종료: 분야별 마스킹 당첨 명단) → 참여 방법·경품·유의사항 순이다.
- 액션·흐름: primary는 단계를 따른다. 모집은 출품하기(비로그인은 로그인 후 출품, 기존 출품자도 추가 출품), 체험은 프로젝트 둘러보기, 발표는 결과 확인이다. 로그인 회원은 보조로 내 참여에 간다.
- 경계·상태: 공개 화면이며 갤러리는 체험 기간의 승인 출품만 보여 준다. 일정 준비 중, 운영 중단, 단계 사이 공백(다음 일정 안내), 검색 결과 없음, 공개 출품 없음을 제공한다.
- 반응형·분석: 360px에서 상태 카드 버튼은 세로로 쌓고, 갤러리는 1/2/3열로 늘린다. 검색·필터는 GET query로 공유 가능해야 한다.
- 수용 기준: 체험 기간 밖에는 프로젝트 카드가 렌더되지 않고, 비활성화와 일정상 공백이 다른 문구로 보인다.

## `/events/project-showcase/projects/new` — 출품

- 목표·위계: 유형 선택 → 서비스 정보·주소 → 대표 이미지 → 출품자 안내(로그인 회원) → 이름 공개 동의 1개 → 제출 순이다.
- 액션·흐름: primary는 출품하기, 보조는 돌아가기다. 비로그인은 로그인 후 복귀하고, 이미 출품한 회원도 새 프로젝트를 등록할 수 있다. 제출 성공 시 내 출품 보기로 간다.
- 경계·상태: 모집 기간·로그인 회원만 제출한다. 모집 기간 아님, 회원 이름 확인 불가, 이미지 저장 실패를 구분해 안내한다.
- 반응형·분석: 유형은 360px 2열·데스크톱 4열, 입력은 모바일에서 세로로 쌓는다.
- 수용 기준: FE와 BE가 같은 검증으로 서비스 정보, https 주소, Embedded 영상 호스트, 이름 공개 동의를 확인하고 첫 오류 필드에 focus한다.

## `/events/project-showcase/my` — 내 참여

- 목표·위계: (발표 시작 후) 당첨 결과 → 내 출품 목록(취소 건 포함, 프로젝트별 상태·집계) → 체험과 추첨권(보유 추첨권, 체험한 프로젝트, 참여 등록 여부, 프로젝트별 피드백 완료·대기) → 당첨 결과 순이다.
- 액션·흐름: 모집 중이면 출품 개수와 관계없이 추가 출품 버튼을 표시한다. 각 카드에서 출품 내용 보기로 이동한다.
- 경계·상태: 본인 데이터만 읽는다. 출품 없음, 확인 대기, 수정 요청(안내 강조), 출품 확정, 출품 불가, 체험 기간 전을 제공한다.
- 반응형·분석: 집계 카드는 모바일 2열·데스크톱 4열이다.
- 수용 기준: 방문자·피드백 작성자 정보가 어디에도 표시되지 않는다.

## `/events/project-showcase/my/projects/[projectId]` — 내 출품 보기

- 목표·위계: 출품 상태와 안내 → 운영진 검수 사유 → 수정·취소 → 받은 반응(조회·체험·피드백·관심 수, 작성자 없는 피드백 본문, 승인 출품만) → 제출 내용(이미지, 설명, 주소) 순이다.
- 액션·흐름: 모집 기간의 확인 대기·수정 요청 상태에서만 수정하기가 primary다. 출품 취소는 모집 기간 내내 확인 단계를 거쳐 실행한다.
- 경계·상태: 소유자가 아니면 404다. 수정 불가 상태에서는 버튼을 노출하지 않는다.
- 반응형·분석: 소개와 버튼은 좁은 폭에서 세로로 쌓는다.
- 수용 기준: 취소는 해당 출품에만 적용하고 다른 출품은 유지한다.

## `/events/project-showcase/my/projects/[projectId]/edit` — 출품 수정

- 목표·위계: 검수 사유 → 출품 폼(기존 값) → 다시 제출 순이다.
- 액션·흐름: primary는 수정해서 다시 제출이며, 성공하면 확인 대기로 돌아가 내 출품 보기로 이동한다.
- 경계·상태: 수정 가능 상태가 아니면 내 출품 보기로 보낸다. 이미지는 바꾸지 않으면 기존 이미지를 유지한다.
- 반응형·분석: 출품 폼과 같은 규칙을 따른다.
- 수용 기준: 수정 제출도 출품과 같은 FE/BE 검증를 거친다.

## `/events/project-showcase/projects/[projectId]` — 프로젝트 상세·체험

- 목표·위계: 대표 이미지 → 유형·이름·팀명·한 줄 소개 → 서비스 소개 → 체험 영역(참여 등록 → 체험 시작 → 1분 뒤 한 줄 피드백, 관심 표시) 순이다.
- 액션·흐름: primary는 단계에 따라 참여 등록하고 체험 시작, 체험 시작, 피드백 남기기로 바뀐다. 체험 시작은 새 탭을 먼저 연 뒤 서버 기록이 끝나면 서비스 주소로 이동한다. 관심 표시는 추첨권과 무관한 보조 토글이다. 보조는 프로젝트 목록 복귀다.
- 경계·상태: 체험 기간 밖에는 프로젝트 내용 없이 체험 기간과 이벤트 링크를 보여 준다. 승인되지 않았거나 없는 프로젝트는 404다. 로그인 회원의 최초 조회만 기록하고 본인·운영자 조회는 제외한다. 비로그인, 본인 프로젝트, 미등록, 체험 전, 1분 대기(남은 초 표시), 피드백 가능, 피드백 완료(추첨권 1장) 상태를 제공한다.
- 반응형·분석: 데스크톱은 본문과 체험 영역 2열, 모바일은 본문 뒤에 체험 영역을 둔다. 남은 시간은 서버 시각 기준으로 계산해 SSR과 hydration이 같은 값을 그린다.
- 수용 기준: 공유된 상세 링크가 체험 기간 밖에서 404가 아닌 안내 화면을 보여 준다. 참여 등록과 피드백은 FE/BE 같은 검증을 쓰고, 1분 전 피드백·중복 피드백·본인 프로젝트 체험은 서버와 DB에서 거절한다.

## `/admin/events` — 이벤트 운영 허브

- 목표·위계: 쇼케이스 상태·집계 → 쇼케이스 운영·로그 이동 → 기존 이벤트 목록 이동 순이다.
- 액션·흐름: primary는 쇼케이스 운영, 보조는 로그·집계와 공개 페이지 보기다.
- 경계·상태: events read 권한이 필요하다. 이벤트 설정 없음 상태를 제공한다.
- 반응형·분석: 집계는 모바일 2열·데스크톱 4열이다.
- 수용 기준: 단계 문구가 공개 허브와 같은 단계 계산을 쓴다.

## `/admin/events/project-showcase` — 쇼케이스 운영

- 목표·위계: 일정·경품 수량 → 상태별 출품 탭 → 출품 카드(내용, 주소, 검수) 순이다.
- 액션·흐름: primary는 검수(현재 상태를 뺀 승인·수정 요청·반려·숨김)다. 일정 저장은 별도 form이다. 중복 출품 사유 넣기는 "이미 등록된 프로젝트입니다"를 채우며, 운영자가 반려를 눌러 확정한다.
- 경계·상태: events read로 조회하고 update 권한에서만 저장·검수한다. 탭별 빈 상태, 일정 순서 오류, 사유 누락 오류를 제공한다.
- 반응형·분석: 상태 탭은 가로 스크롤, 출품 카드는 모바일에서 이미지 위·내용 아래로 쌓는다. 일정 변경과 검수를 audit한다.
- 수용 기준: 수정 요청과 반려는 FE/BE 모두 사유 없이 저장되지 않고, 사유는 출품자 화면에 그대로 보인다.

## `/admin/events/project-showcase/logs` — 쇼케이스 로그·집계

- 목표·위계: 전체 집계 → 출품 상태·유형 → 승인 프로젝트별 집계 → 활동 로그(유형 필터, cursor 페이지) 순이다.
- 액션·흐름: primary는 활동 유형 필터, 보조는 이전 로그 더 보기와 최신으로 돌아가기다.
- 경계·상태: events read 권한이 필요하다. 로그에는 회원 ID, 학번, IP, User-Agent, 피드백 작성자가 없다.
- 반응형·분석: 로그 행은 모바일에서 시각을 아래로 내린다.
- 수용 기준: 잘못된 cursor와 유형 query는 무시하고 첫 페이지를 보여 준다.

## `/admin/events/project-showcase/feedback` — 쇼케이스 피드백 관리

- 목표·위계: 공개 중·숨김 탭 → 피드백 목록(프로젝트명, 작성 시각, 본문) 순이다.
- 액션·흐름: primary는 숨기기(숨김 탭에서는 다시 공개)다. 보조는 쇼케이스 운영 복귀다.
- 경계·상태: events read로 조회하고 update 권한에서만 바꾼다. 작성자 정보는 표시하지 않는다. 탭별 빈 상태와 처리 오류를 제공한다.
- 반응형·분석: 모바일은 본문 아래 버튼, 데스크톱은 오른쪽 버튼이다. 공개 상태 변경을 audit한다.
- 수용 기준: 숨긴 피드백은 출품자 화면에서 사라지지만 유효 체험 수와 추첨권은 바뀌지 않는다.

## `/admin/events/project-showcase/draw` — 검증·추첨·발표

- 목표·위계: 진행 상태(단계, 출품·체험 추첨 여부, 정산·파기 예정일) → 출품 후보(승인 출품, 제외·당첨 표시) → 체험 후보(이름, 추첨권) → 당첨자(무효·재추첨·발송) → Mattermost 공지 문구 → 정산 순이다.
- 액션·흐름: primary는 현재 순서의 추첨 실행(출품 먼저, 체험 나중)이며 확인 단계를 거친다. 보조는 후보 제외·복구(사유 필수), 무효 처리(중복·수령 불가·검증 실패) 후 1명 재추첨, 발송 완료 표시, 공지 문구 복사, 정산 완료 기록이다.
- 경계·상태: events read로 조회하고 update 권한에서만 바꾼다. 체험 종료 전, 추첨 완료, 순서 위반, 후보 없음(미집행), 정산 완료 뒤 잠금, 파기 완료를 제공한다. 공개 명단과 공지 문구는 마스킹 이름만 쓴다. 회원 조회 권한이 있는 관리자에게 당첨자 회원 화면 링크를 제공해 기존 연락처로 구글폼을 안내한다.
- 반응형·분석: 후보·당첨 행은 모바일에서 컨트롤을 아래로 내린다. 제외·추첨·무효·재추첨·발송·정산을 audit한다.
- 수용 기준: 추첨은 서버 CSPRNG로 출품은 프로젝트마다 1장을 부여해 뽑고 당첨 회원의 나머지 표본을 제거하며, 체험은 추첨권 가중으로 뽑고, 한 사람은 두 분야를 통틀어 유효 당첨 1건을 넘지 않으며, 이 규칙은 서버와 DB에서 다시 검사한다.
